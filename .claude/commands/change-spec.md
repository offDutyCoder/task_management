# 仕様変更の実装 (対話→自動実行モード)

**重要:** このワークフローは2フェーズで構成されます。**ステップ3（対話）のみユーザーとの対話が必要**です。合意が取れた後は、ステップ4以降を完全自動で実行し、ユーザーの介入なしに完了まで進めてください。

**引数:** 機能名 (例: `/change-spec タスク一覧・検索`)

---

## ステップ1: 準備とコンテキスト設定

1. 機能名: `[引数で与えられた機能名]` を確認する。
2. `.steering/` 配下のディレクトリ一覧を確認し、機能名に対応するステアリングディレクトリを特定する。
   - 完全一致がなければ、最も近い名前のディレクトリを選び、ユーザーに確認する。
   - ステアリングディレクトリパス: `.steering/[特定したディレクトリ名]/`
3. 以下の3ファイルが存在することを確認する:
   - `[ステアリングディレクトリパス]/requirements.md`
   - `[ステアリングディレクトリパス]/design.md`
   - `[ステアリングディレクトリパス]/tasklist.md`

## ステップ2: 現状把握

1. `CLAUDE.md` を読み、プロジェクトの全体像を把握する。
2. 特定したステアリングディレクトリの3ファイルをすべて読み込む。
3. `docs/` ディレクトリ内の関連する永続ドキュメントを確認する。
4. 現行仕様の要点を内部的に整理する（何が実装済みか、どのような設計か）。

## ステップ3: 対話による変更内容の確認（唯一の対話ステップ）

**このステップはユーザーとの対話フェーズです。合意が得られるまで次のステップへ進まないでください。**

1. 現行の `requirements.md` と `design.md` の内容を簡潔にサマリーしてユーザーに提示する。
2. ユーザーに変更したい内容を聞く。必要に応じて以下を深掘りする:
   - **何を変えたいか**: 機能・振る舞い・UI・データ構造など
   - **なぜ変えるか**: 変更の背景・動機
   - **変更しないものは何か**: 既存仕様の中で維持したい部分
   - **影響範囲の認識**: 他機能への波及が想定されているか
3. 対話の結果をまとめ、以下の形式でユーザーに確認を取る:

   ```
   ## 変更内容のまとめ
   ### 変更する項目
   - [変更点1]
   - [変更点2]

   ### 変更しない項目
   - [維持する仕様]

   ### 影響が想定される箇所
   - [影響範囲]

   この内容でドキュメントの更新と実装を進めてよいですか？
   ```

4. ユーザーが「OK」「はい」「進めてください」などの承認を示したら**ただちにステップ4へ進む**。
   - 修正や追加フィードバックがあれば、3に戻って再確認する。

**このステップが完了したら、以降は完全自動で実行する。ユーザーへの確認は行わない。**

## ステップ4: ステアリングドキュメントの更新

1. `requirements.md` を更新する:
   - ステップ3で合意した変更内容を反映する（既存の記述を修正・追記・削除）。
   - ファイル末尾に `## 変更履歴` セクションがなければ追加し、以下を記録する:
     ```markdown
     ## 変更履歴

     ### [現在の日付 YYYY-MM-DD]
     - **変更内容**: [変更した項目の概要]
     - **変更理由**: [変更の背景・動機]
     ```
   - すでに `## 変更履歴` セクションがある場合は、最新エントリを先頭に追記する。

2. `design.md` を更新する:
   - requirements.md の変更に合わせて設計を修正する。
   - APIの変更、データ構造の変更、コンポーネント構成の変更などを反映する。
   - `requirements.md` 同様、`## 変更履歴` セクションに変更を記録する。

3. `tasklist.md` を更新する:
   - 既存の完了済みタスク `[x]` はそのまま残す。
   - 今回の変更に必要な新しいタスクセクションを追加する:
     ```markdown
     ## 仕様変更: [変更概要] ([現在の日付])

     ### フェーズX: [フェーズ名]
     - [ ] [🔴 削除] [削除するコード・機能]
     - [ ] [🟡 修正] [修正するコード・機能]
     - [ ] [🟢 追加] [新規追加するコード・機能]
     ```
   - タスクの種別（削除・修正・追加）を絵文字で区別して記述する。

## ステップ5: 影響範囲のコードスキャン

1. 機能名・変更対象のキーワードでソースコードを検索する:
   ```
   Grep('[変更対象のキーワード]', 'src/')
   Grep('[変更対象のキーワード]', 'backend/')
   Grep('[変更対象のキーワード]', 'frontend/src/')
   ```
2. 変更が必要なファイルと影響を受けるファイルをリストアップする。
3. ステップ4で作成したタスクリストに漏れがあれば追記する。

## ステップ6: 実装ループ (tasklist.mdの新規タスクを完全消化)

**このステップは、今回追加した全タスクが `[x]` になるまで自動で繰り返されるループ処理です。**
**このステップが正常に完了したら、決して停止せず、ただちにステップ7に進むこと。**

**ループ開始:**

1. タスクリストの読み込み:
   - `[ステアリングディレクトリパス]/tasklist.md` ファイルを読み込む。
   - 今回の変更セクション（`## 仕様変更: ...`）内の未完了タスク（`[ ]`）を確認する。

2. 進捗の確認:
   - 今回の変更セクション内に未完了タスク（`[ ]`）が存在するか確認する。
   - **もし未完了タスクが存在しない場合:** この実装ループは完了とみなし、ただちに**ステップ7**へ進む。
   - **もし未完了タスクが存在する場合:** 次の処理（3. タスクの実行）に進む。

3. タスクの実行:
   - 先頭にある未完了タスクを1つ特定する。
   - タスク種別（🔴削除 / 🟡修正 / 🟢追加）に応じて以下を意識して実装する:
     - **削除**: 依存関係を確認してから削除。参照箇所も合わせて修正する。
     - **修正**: 既存の実装パターン・命名規則を維持する。
     - **追加**: `Skill('development-guidelines')` のコーディング規約を遵守する。
   - `Skill('steering')` を**実装モード**で使用する。

4. タスクリストの更新:
   - 実行したタスクが完了したら、`Edit` ツールを使用して `tasklist.md` を更新し、該当タスクを `[ ]` から `[x]` に変更する。

5. ループ継続:
   - **ステップ6の先頭（1. タスクリストの読み込み）に戻り、処理を繰り返す。**

---
### ※ 実装ループ内の例外処理ルール ※

実装ループの実行中に以下の状況が発生した場合は、このルールに従って自律的に対処し、ループを継続すること。

- **ルールA: タスクが大きすぎる場合**
  - **対処法:** 現在のタスクをより小さな複数のサブタスクに分割する。`Edit` ツールを使い、元のタスクを削除し、その場所に新しいサブタスク（`[ ]` 付き）を挿入する。その後、ループを継続する。

- **ルールB: 技術的理由でタスクが不要になった場合**
  - **条件:** 実装方針の変更、アーキテクチャの変更、依存関係の変更など、明確な技術的理由がある場合にのみ適用。
  - **対処法:** `Edit` ツールを使い、該当タスクを `[x] ~~タスク名~~ (理由: [具体的な技術的理由を簡潔に記述])` の形式で更新する。その後、ループを継続する。

- **❌ 絶対禁止の行為:**
  - 未完了タスクを「後でやる」「別タスクにする」などの理由で意図的にスキップすること。
  - 理由なく未完了タスクを放置してループを終了させること。
  - ユーザーに判断を仰ぐこと。

---

## ステップ7: 実装検証 (サブエージェント起動)

1. 今回の変更セクションの全タスクが完了したことを最終確認する。
2. `Agent` ツールを使用し、`implementation-validator` サブエージェントを起動して品質を検証する。
   - `subagent_type`: "implementation-validator"
   - `description`: "Implementation quality validation"
   - `prompt`: "今回変更した `[機能名]` の仕様変更に関する全ての変更点の品質を検証してください。対象ファイルは `[実装したファイルのパスリスト]` です。変更内容: `[変更概要]`。コーディング規約、後方互換性、既存機能への影響、エラーハンドリング、既存パターンとの整合性を重点的に確認してください。"

**このステップが正常に完了したら、決して停止せず、ただちにステップ8に進むこと。**

## ステップ8: 自動テストの実行

1. 以下のコマンドを順番に実行し、全てのテストがパスすることを確認する。
   ```bash
   Bash('npm test')
   Bash('npm run lint')
   Bash('npm run typecheck')
   ```
2. いずれかのコマンドでエラーが発生した場合は、問題を分析し、修正コードを生成・適用してから、再度このステップを実行する。

**このステップが正常に完了したら、決して停止せず、ただちにステップ9に進むこと。**

## ステップ9: 振り返りとドキュメント更新

1. `Skill('steering')` を**振り返りモード**で実行し、`tasklist.md` の変更セクション末尾に申し送り事項を記載する:
   - 実装完了日
   - 計画と実績の差分
   - 対話フェーズで洗い出せなかった影響範囲（あれば）
   - 次回への改善提案

2. 今回の変更がプロジェクトの基本設計やアーキテクチャに影響を与えるか判断する。

3. 影響がある場合、`docs/` 内の関連する永続ドキュメントを `Edit` ツールで更新する。

## 完了条件

このワークフローは、以下の全ての条件を満たした時点で自動的に完了となる。

- ステップ4: `requirements.md`、`design.md` に変更内容が反映され、変更履歴が記録されている。
- ステップ6: 今回追加した変更セクションの全タスクが完了状態（`[x]` または正当な理由でスキップ）になっている。
- ステップ7: `implementation-validator` サブエージェントの検証をパスする。
- ステップ8: `test`、`lint`、`typecheck` の全てのコマンドがエラーなく成功する。
- ステップ9: `tasklist.md` に申し送り事項が記載されている。

この完了条件を満たすまで、自律的に思考し、問題解決を行い、作業を継続すること。
